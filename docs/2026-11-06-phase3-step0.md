# 2026-11-06 — Phase 3 step 3.0: mailbox/window dump after FW_READY (read-only; no IPC sent)

Boot-args `dmic_p2=1 dmic_p3_dump=1`. Raw: `logs/phase3-0-ioreg.txt`. Result: FW_READY again, clean teardown (final ADSPCS 0x00000f0f), no panic, no hang.

## Observed
- FW_READY at BAR4+0x81000 as before: size 108, cmd 0x70000000, version 2.2.0, ABI 0x03016001 (word 16 at +0x40 confirmed).
- **No extended data follows the 108-byte message** (`ext[0]` at +108: size=0, cmd=0). So FW_READY does not announce the window layout at runtime.
- DOWNBOX (0xA0000), DEBUG (0xC0000), EXCEPTION (0xC0800), STREAM (0xC1000), TRACE (0xE0000) heads all read 0 (untouched yet; no fault reading them).
- REGS +0x00 = 0x00000005 (ROM_STATUS = FW_ENTERED), +0x04 = 0, +0x08 = 0x4000, +0x18 = 0x01830194 (meaning unknown).

## Conclusion
Linux gets the window table from the **extended manifest inside `sof-cnl.ri`** at load time (`ipc3-loader.c:190`, `SOF_EXT_MAN_ELEM_WINDOW` -> `sof_ipc3_get_ext_windows`),
not from FW_READY, and `ipc3_get_windows` (`ipc3.c:647`) uses it afterwards. That is the table decoded in Phase 0 (recipe §6):
UPBOX 0x81000, DOWNBOX 0xA0000, DEBUG 0xC0000, EXCEPTION 0xC0800, STREAM 0xC1000, TRACE 0xE0000. Step 3.1 will use those values, verified against the
manifest of the exact file in /Library (sha256 c5119cfc…359e); the kext should parse the manifest itself rather than hard-code offsets.
